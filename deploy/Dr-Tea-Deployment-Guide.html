01Overview & comparison

Every deploy method uses the same Dockerfile at the repo root as the universal contract. Nothing in the application code changes when you switch hosting. The differences are only in who orchestrates the container.

MethodBest forSetup timeRecurring effortLock-in
A · Manual VPS Maximum control, lowest cost, full freedom ~15 min SSH + one command per deploy None
B · GitHub auto-deploy Push-to-deploy with safety rails +10 min on top of A Just git push None
C · Coolify You already run Coolify and want a UI ~5 min Click "Deploy" in dashboard Owns ports 80/443
Recommendation

Start with Method A, then layer Method B once you're comfortable. Use Method C only if you specifically want a web dashboard and are OK with Coolify managing all your sites on the box.

02Prerequisites

You'll need these regardless of which method you pick.

  • A domain name you control (e.g. drtea.in)
  • DNS access to your domain (in your registrar's dashboard)
  • A VPS running Ubuntu 22.04 or 24.04 with at least 2 GB RAM
    • Hetzner CX22 — €4.51/month (recommended)
    • DigitalOcean Basic — $6/month
    • Vultr / Linode / OVH — any equivalent works
  • Root SSH access to that VPS
  • Your GitHub repo: vedictatvaaa/DRTEAFINAL

03Method A — Manual VPS install

The install.sh script does everything: installs Docker, generates secrets, fetches your code, starts Postgres + API + Caddy, and obtains free Let's Encrypt TLS certificates.

1

SSH into your fresh VPS

From your laptop or any terminal:

ssh root@YOUR_VPS_IP

Enter the root password your VPS provider gave you when prompted.

2

Run the one-line installer

Copy and paste this exactly:

curl -fsSL https://raw.githubusercontent.com/vedictatvaaa/DRTEAFINAL/main/deploy/install.sh | bash

It will interactively ask you for:

  • Domain — e.g. drtea.in
  • Email — used by Let's Encrypt for cert expiry warnings
  • Repo URL — press Enter to accept the default

Then it runs unattended for ~5–10 minutes: installing Docker, pulling code, building images, starting the stack.

3

Point your DNS at the VPS

In your domain registrar's DNS dashboard, add two A records:

TypeNameValueTTL
A@YOUR_VPS_IPAuto / 300
AwwwYOUR_VPS_IPAuto / 300

Propagation takes 1–10 minutes (sometimes longer for slow registrars).

4

Verify the site is live

Visit https://your-domain.com in a browser. First visit triggers automatic TLS certificate issuance — give it 20–30 seconds.

Then verify the API:

curl https://your-domain.com/api/healthz

Expected response: {"status":"ok"}

What the installer creates on your VPS

PathWhat it is
/opt/drtea/Root directory for the app
/opt/drtea/.envAuto-generated secrets (DB password, session secret, admin password)
/opt/drtea/standalone/Compose file + Caddy config
/opt/drtea/state/last-good-shaLast commit that passed health check (for rollback)
/usr/local/bin/drteaThe drtea CLI for managing the stack
Important

The auto-generated admin password is written to /opt/drtea/.env. Print it on first install with: grep ADMIN_PASSWORD /opt/drtea/.env — save it to your password manager immediately.

04Method B — GitHub auto-deploy

Once Method A is set up, layering this on means every git push to main automatically deploys to your VPS — with three security failsafes so a bad push can't take you down.

What protects you

  • Author allowlist — only commits from approved GitHub usernames trigger a deploy
  • Sensitive-path guard — pushes that touch deploy/, Dockerfile, .env*, lockfiles, or workflows are blocked from auto-deploy (manual review needed)
  • Health-check + auto-rollback — after deploying, the workflow calls /api/healthz. If it's not 200 OK, the VPS auto-rolls back to the last known-good commit
  • GitHub Issues opened on failure or block — you always know what happened
1

Generate an SSH key just for the Action

On your laptop (or in Replit Shell), run:

ssh-keygen -t ed25519 -C "github-actions-drtea" -f ~/.ssh/gh_drtea -N ""

This creates two files:

  • ~/.ssh/gh_drtea — the private key (goes into GitHub)
  • ~/.ssh/gh_drtea.pub — the public key (goes onto VPS)
2

Authorize the public key on your VPS

Print the public key:

cat ~/.ssh/gh_drtea.pub

Copy the entire line. Then SSH into your VPS and run:

ssh root@YOUR_VPS_IP
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo "PASTE_PUBLIC_KEY_LINE_HERE" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
exit

Verify it works from your laptop:

ssh -i ~/.ssh/gh_drtea root@YOUR_VPS_IP "echo connected"

If you see connected (no password prompt), proceed.

3

Add secrets & variable to GitHub

Go to: https://github.com/vedictatvaaa/DRTEAFINAL/settings/secrets/actions

Secrets tab — click "New repository secret" and add all three:

NameValue
VPS_HOSTYour VPS IP address
VPS_USERroot
VPS_SSH_KEYThe full contents of ~/.ssh/gh_drtea (including -----BEGIN… and -----END… lines)

Variables tab — click "New repository variable":

NameValue
ALLOWED_AUTHORSYour GitHub username (for multiple, comma-separated, no spaces: user1,user2)
4

Push code and watch it deploy

Make any small change and push:

git add .
git commit -m "test: verify auto-deploy"
git push origin main

Open https://github.com/vedictatvaaa/DRTEAFINAL/actions — you'll see the workflow run with three jobs:

  1. guard — verifies you're an allowed author and no sensitive files changed
  2. deploy — SSHes into the VPS, pulls code, rebuilds, health-checks
  3. notify-failure — runs only if something broke (opens a GitHub Issue)

Manual override always available

Even with auto-deploy on, you can always deploy manually by SSHing in and running drtea update --safe. The Action and the manual CLI don't conflict.

05Method C — Coolify (UI)

Coolify is a self-hosted dashboard that gives you a UI for Docker deployments. Useful if you already run it for other sites.

Heads up

Coolify takes exclusive control of ports 80/443 on the VPS via its built-in proxy. You can't run our standalone stack on the same machine as Coolify. They will fight for the same ports.

1

Add new resource

In your Coolify dashboard: "+ New Resource" → "Public Repository".

2

Configure the source

  • Repository: https://github.com/vedictatvaaa/DRTEAFINAL
  • Branch: main
  • Build pack: Dockerfile (Coolify auto-detects)
  • Port: 8080
3

Set domain & environment

Enter your domain in Coolify's domain field — Coolify handles TLS automatically.

Add these environment variables in the UI:

VariableValue
DATABASE_URLYour Postgres connection string (Coolify can provision Postgres for you)
SESSION_SECRETRandom 32+ character string
ADMIN_PASSWORDYour admin login password
4

Deploy

Click Deploy. Coolify will auto-redeploy on every push to main going forward.

Files unused in Coolify mode

When using Coolify, these files in the repo are simply ignored (harmless to leave in):

  • deploy/install.sh
  • deploy/standalone/*
  • .github/workflows/deploy.yml — disable by renaming to deploy.yml.disabled if you don't want it firing

06The drtea command reference

Installed by install.sh at /usr/local/bin/drtea. Available on the VPS via SSH.

CommandWhat it does
drtea statusShows which containers are running and their health
drtea logsTails the container logs (Ctrl+C to exit)
drtea logs apiLogs from just the API container
drtea logs caddyLogs from just the Caddy reverse proxy
drtea updatePull latest code and restart (no safety check)
drtea update --safeUpdate, run health check, auto-rollback on failure
drtea update --safe --ref <sha>Deploy a specific commit SHA
drtea rollbackRevert to the last known-good commit (stored in /opt/drtea/state/last-good-sha)
drtea healthHit /api/healthz and print the result
drtea restartRestart all containers
drtea stopStop all containers (site goes offline)
drtea startStart all containers

07DNS & domain setup

Whether you use GoDaddy, Namecheap, Cloudflare, or Google Domains, the records are the same:

TypeHost/NameValue/TargetTTL
A@ (root)Your VPS IP300 or "Auto"
AwwwYour VPS IP300 or "Auto"

If you use Cloudflare

Set the orange-cloud proxy to OFF (gray cloud / "DNS only") for both records when you're issuing TLS certs the first time. Caddy needs direct access to validate ownership. Once the cert is issued you can re-enable proxy if desired.

How to check propagation

dig +short your-domain.com

Should return your VPS IP. If it doesn't, wait a few more minutes.

08Secrets & environment variables

All secrets live in /opt/drtea/.env on the VPS. The installer auto-generates strong values for them.

VariablePurposeDefault
POSTGRES_PASSWORDPostgres root passwordAuto-generated (32 chars)
DATABASE_URLApp connection stringBuilt from above
SESSION_SECRETSigns login session cookiesAuto-generated (64 chars)
ADMIN_PASSWORDAdmin panel passwordAuto-generated (16 chars)
DOMAINYour site's domainYou provide during install
ACME_EMAILLet's Encrypt notification emailYou provide during install

Viewing or changing a secret

ssh root@YOUR_VPS_IP
nano /opt/drtea/.env
# edit, save (Ctrl+O, Enter, Ctrl+X)
drtea restart
Never

Commit .env to git. It's listed in .gitignore already — keep it that way. If you need to back up these values, store them in a password manager (1Password, Bitwarden).

09Health checks & rollback

The app exposes a simple health endpoint used by every deploy method to verify the site is alive.

GET https://your-domain.com/api/healthz
→ 200 OK
{"status":"ok"}

How auto-rollback works (Methods A & B)

  1. Before deploying a new commit, the current SHA is saved to /opt/drtea/state/last-good-sha
  2. New code is pulled, containers rebuilt and restarted
  3. Script polls /api/healthz for up to 60 seconds
  4. If healthy → save new SHA as last-good, done
  5. If unhealthy → check out the last-good SHA, rebuild, restart
  6. Method B additionally opens a GitHub Issue describing the failure

Manual rollback any time

drtea rollback

10Switching between methods

The repo never has to change. You can move between methods at will.

From → ToSteps
A → B Just do Method B setup on top. Method A keeps working as a fallback for manual emergencies.
A or B → C 1. Stop the standalone stack: drtea stop
2. Install Coolify on the same VPS (or fresh)
3. Add Dr Tea as a Coolify resource pointing at the repo
C → A 1. Spin up a fresh VPS
2. Run install.sh on it
3. Point DNS at the new VPS
4. Decommission the Coolify deployment at your leisure

11Troubleshooting

SymptomWhat to check
Site won't load at alldrtea status — are containers running? drtea logs for errors.
"Connection refused" in browserCaddy not running. drtea restart. If still broken, check VPS firewall allows 80/443.
TLS / certificate errorDNS not pointing at VPS yet. Run dig +short your-domain.com — must show VPS IP. Then drtea restart.
API returns 500drtea logs api — usually missing env var or DB migration not run.
API returns 502 from CaddyAPI container not ready. drtea logs api — wait for "server listening on 8080".
GitHub Action failsOpen the Actions tab → click failed run → expand red step. Most common: VPS_SSH_KEY secret missing or malformed (must include BEGIN/END lines).
Deploy rolled back unexpectedlydrtea logs shows which release failed health check. Check GitHub Issue (Method B opens one automatically).
Need to revert manuallydrtea rollback
Lost admin passwordssh root@YOUR_VPS_IP "grep ADMIN_PASSWORD /opt/drtea/.env"
VPS running out of diskdocker system prune -a -f (removes unused images)
